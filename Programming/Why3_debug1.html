Failure

Lets say we have such WhyML code: 

module Call1
  use int.Int

  type trace = { mutable f1_calls: int }

  let ghost trace : trace = { f1_calls = 0 }

  predicate f1_was_called (before after: int) = after = before + 1
  predicate f1_was_not_called (before after: int) = after = before  

  let ghost f1 () : unit
    writes { trace.f1_calls }
    ensures { f1_was_called (old trace.f1_calls) trace.f1_calls }
  =
    trace.f1_calls <- trace.f1_calls + 1

  let f2 (a1: int) : int
    writes { trace.f1_calls }
    ensures { result = if a1 = 0 then 100 else 101 }
    ensures { a1 = 0 -> f1_was_not_called (old trace.f1_calls) trace.f1_calls }
    ensures { a1 <> 0 -> f1_was_called (old trace.f1_calls) trace.f1_calls }
  = if a1 = 0 then begin
     f1 ();
     100
    end
    else begin
      f1 ();
      101
    end

  let main () : unit
    requires { trace.f1_calls = 0 }
    ensures { trace.f1_calls = 0 }
  =
    let _ = f2 0 in
    ()

end

it is explained here. If to prove it: 

$ why3 prove Call1.mlw -P z3 
File Call1.mlw:
Goal f1'vc.
Prover result is: Valid (0.00s, 38 steps).

File Call1.mlw:
Goal f2'vc.
Prover result is: Unknown (sat) (0.00s, 258 steps).

File Call1.mlw:
Goal main'vc.
Prover result is: Valid (0.00s, 40 steps).

i.e., f2 cannot be proven. What does it mean?

Messages

See this - it is the source code of Why3 describing possible values of a prover result - one of them is Unknown: 

type prover_answer = 
| Valid                   (* The task is valid according to the prover *)
| Invalid                 (* The task is invalid *)
| Timeout                 (* The task timeouts, ie it takes more time than specified *)
| OutOfMemory             (* The task runs out of memory *)
| StepLimitExceeded       (* The task required more steps than the limit provided *)
| Unknown of string       (* The prover can't determine if the task is valid *)
| Failure of string       (* The prover reports a failure *)
| HighFailure of string   (* An error occured during the call to the prover
                             or none of the given regexps match the output of the prover *)

Why3 forms a request to SMT and the result of SMT is "sat": 

Prover result is: Unknown (sat) (0.00s, 258 steps).
                           ^^^
                         t h i s

There are 2 different questions a solver can ask about a Why3 verification condition (VC):

  • Is the formula satisfiable (sat)? Can it be true under some assignment of values?
  • Is the formula unsatisfiable (unsat)? Is there no assignment of values that makes it true?

For verification, Why3 normally wants to prove that the VC is valid. An equivalent way to do that is to ask whether its negation is unsatisfiable.

So, possible answers of SMT in short are:

Solver result Meaning for verification
unsat No counterexample exists; the VC is proved.
sat A counterexample exists; the VC is not valid.
unknown The solver cannot decide.

Why3 translates the prover's responses into its own result categories, including Valid, Invalid, and Unknown - see prover answer.

So, the result is "The prover can't determine if the task is valid", and SMT returned "sat".

What is this? This is a successful prof treating by Why3 as proving that f2 is Unknown. Why? Because a1=0 /\ ... and a1≠0 /\ ... are ensures {..} in our f2:

This is the first way to understand the reason of Unknown.

2 separate conclusions:

  • calls of functions (like of f1()) usually are replaced by their postconditions (if they were declared)
  • as you see SMT request could be simplified before to be form for SMT, but Why3 did not do it, it means that more strict logical description of situation (more asserts, invariants, ...) can help to make the request more optimal. It makes sense when you hit timeouts, out of memory, too slow prooving...

Debug output

Yet another approach for debugging is to use a special --debug CLI option (it requires different flags, you can see them with --list-debug-flags): 

$ why3 prove Call1.mlw -P z3 --debug vc_debug

The output is an intermediate language used internally by Why3's VC generator, so syntax forms like HAVOC, VAL, STOP, WITH, etc. are part of Why3's internal program representation/VC-generation language:

It is how Why3 symbolically processes program expressions and constructs verification conditions (VC).

Symbolic execution

Symbolic execution is evaluating a program using symbolic values and logical constraints instead of running it with concrete inputs.

For example, WhyML is: 

if a1 = 0 then
  100
else
  101

A normal execution might use the variable a1 = 0, choose the first branch, and return 100.

Symbolic execution leaves a1 unknown and explores the two possible cases: 

          Initial symbolic state:             
             • a1: int                        
             • trace.f1_calls: int            
                      |                       
          Test the condition a1 = 0           
                   /    \                     
                  /      \                    
             a1 = 0    a1 <> 0                
                /          \                  
       first branch       second branch       
       symbolic expr      symbolic expr

Each branch has its own path condition and symbolic state.

Why3 uses symbolic reasoning to construct a formula that expresses what must be true for the program to satisfy its specification. Its VC generator uses weakest-precondition calculus by default, with a strongest-postcondition mode also available.

It is like integer integration, using a series or an analytical solution to the integral - resulting in a new formula.

E.g., HAVOC { trace @rho -> { f1_calls1 -> []; }}; does not do any calls, it describes an abstraction of a mutable-state update during VC generation. It isn't a runtime instruction that randomly changes the counter. And STOP trace1.f1_calls = 0 marks the terminal verification formula for that symbolic computation. It doesn't mean that execution of main stopped at runtime.

The next listing contain some tokens of this internal representation, it is not 100% stable, so, I suppose, it can changes lesser or more in the next versions, but the short brief table of them:

Token Meaning in this trace
K VAL Introduces a symbolic evaluation case; K is part of the internal trace notation
LET x = e Binds a generated symbolic name to an expression
IF .. THEN .. ELSE .. Processes the two conditional branches symbolically
HAVOC { .. } Represents an abstract update to the symbolic memory/state
VAL .. WITH .. Introduces a value together with logical conditions associated with it
STOP formula Ends this symbolic evaluation with a verification formula to establish
vars = .. Displays a mapping between symbolic variables/states
regs = .. Displays a mapping for symbolic memory regions

Lines 1..6 are the creating (constructing) of the ghost variable trace with the initial value 0 for f1_calls. STOP true means the symbolic execution has reached a terminal condition whose verification formula is true - at the beginning there was K VAL ; introducing a symbolic evaluation of a value expression (the semicolon represents the empty or unit result in this context).

Lines 7..18 is the verification of the body of f1:

  • Line 7: Begins evaluation of the function body, whose result is unit: _.
  • Line 8: Binds trace to the current symbolic record trace1.
  • Line 9: Introduces the increment, 1.
  • Line 10: Reads the current counter, trace1.f1_calls.
  • Line 11: Gives that value another generated name.
  • Line 12: Computes the incremented value, o2 + o1.
  • Line 13: Names the result of the addition.
  • Line 14: HAVOC updates the symbolic memory model to account for the write to trace.f1_calls. The new field value is o3. It does not mean that the counter is randomly modified; the preceding arithmetic determines its new value.
  • Line 15: Introduces the unit result of f1.
  • Line 16: Checks the postcondition f1_was_called (trace.f1_calls) (trace1.f1_calls) in this internal representation. Notice the ordering of the two record expressions here; the surrounding state substitutions matter when interpreting it.
  • Line 17: Records the mapping trace1 -> trace2.
  • Line 18: Records the corresponding mapping for the memory region trace @rho.

Then, the verification of f2:

  • Line 19: Begins symbolic evaluation of f2.
  • Line 20: Introduces the parameter a1.
  • Line 21: Saves the current record state in trace3. This is useful for expressing postconditions relative to the initial state.
  • Line 22: Introduces the constant zero.
  • Line 23: Computes the branch condition, a1 = 0.
  • Line 24: Names the Boolean result of the equality.
  • Line 25: Starts symbolic execution of the conditional. Both branches are analyzed.

and then:

  • Line 26: Introduces the unit argument () passed to f1().
  • Line 27: Captures the current record state as trace4.
  • Line 28: Havocs the mutable field in the symbolic memory model to account for the callee's declared write effect. The empty list [] here is part of the internal representation of the update; it does not mean that the call has no effect.
  • Line 29: This is the key line for the call to f1() in the first branch. VAL _1 WITH .. introduces a symbolic result together with the logical contract condition associated with the call. The predicate f1_was_called describes the relationship between the states.
  • Line 30: Binds the result of the call to the generated variable f1'result. Since f1 returns unit, this is not an integer result.
  • Line 31: Evaluates the branch's result to 100.

Notice the difference from lines 10..14: here, where we call f1, Why3 does not symbolically execute the arithmetic in the body of f1 like imperative languages do it. Instead, it models the call using the callee's effects and contract. This is the modular treatment of the function call.

  • Line 33: Captures the state in trace5.
  • Line 34: Accounts for the callee's mutable-state effect.
  • Line 35: This is the key line for the call to f1() in the else branch. The same postcondition is associated with this call.
  • Line 36: Binds the unit result.
  • Line 37: Evaluates the branch result to 101.

  • Line 61: Reports the prover result. "Unknown (sat)" means the prover did not establish the goal as valid; the parenthesized sat indicates a satisfiable counterexample condition in this output format. It is not a proof that the goal is valid.

Check the documentation and this (includes also transformations) but in general no official documentation on the internal representation so I used AI to extract this info.

OK, then, can we find the problem analyzing vc_debug listing? Yes, look:

  • Line 25 is our if a1 = 0
  • Line 29 is the postcondition of the call of f1 in the positive if branch
  • Line 35 is the same but in the negative if branch
  • so in both if branches f1 is "called" (symbolically)
  • but the postcondition of f2 (line 38: STOP ..) is a conjunction including check f1_was_not_called for a1=0. It is the original f2's postcondition ensures { a1 = 0 -> f1_was_not_called (old trace.f1_calls) trace.f1_calls }

It literally corresponds to the original Why3. This is how Why3 treats it when it does "symbolic execution" and this is the problem with f2. Well, remember: this example is very simple, you can find the problem directly in Why3...

OK, then Why doesn't Why3 reject main too? It cannot be satisfied, right? No, bcs these are separate proof obligations:

Proof obligation What Why3 uses Expected outcome
f2'vc The implementation of f2 and its postconditions Fails: the first branch calls f1 but promises not to
main's VC The precondition of main and the declared contract of f2 Can succeed: f2 promises to preserve the counter for argument zero

The distinction is important: the caller's VC does not automatically inherit the implementation-level failure of the callee. It trusts the callee's contract for modular reasoning.

Ideas for AI

You can pass all outputs to AI so it helps you to analyze it: the better together with WhyML original code. AI understands internal representation of the symbolic execution as well as SMT traces (queries), especially since their languages are good documented.

A counterexample is most useful when it gives a concrete input or branch choice. It may be incomplete or awkwardly named, and it can include values that are irrelevant to the failure.

Finally, "Unknown (sat)" means the prover produced a satisfying model for the negated VC, but Why3/Z3 could not establish a proof. In this case, the sat model is the useful part: it exhibits the failing case.
