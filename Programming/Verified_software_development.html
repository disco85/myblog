Use cases of proof assistants

All use cases can be grouped to:

  1. formalizing mathematics, mathematical foundations, physics, economics, etc
  2. verification of algorithms, models, specifications, software, hardware, certification, etc
  3. control of AI results, improvement of AI results, etc
  4. software development, hardware development, etc

4-th - software development is in the focus of this article. It is not just proving, verifying of some properties of some theories, models, algorithms, etc - IT IS CREATION OF SOFTWARE. Yes, theorem provers, proof assistants (lets call them PA) can be used to... WRITE SOFTWARE... and they are already used today -

you can start with "The Best New Programming Language is a Proof Assistant".

How does it happen? Mostly - via compilation and extraction: 

                  special language
 (sometimes allows traditional programming language)
                         |
                         v
                  proof assistant
                developing software
                         |
           .-------------+-------------.
           |                           |
           v                           v
      compilation                  extraction
          to                           to
      executable                some programming
                                    language

Some of PA support compilation, some - extraction, some - both. Some of them can execute the PA code directly (eg, Why3), some of them understand more than 1 input language, including traditional programming languages (Why3 is such PA!).

The ultimate idea is that you get very safe, verified software which is safe not bcs it uses runtime mechanisms like automatic memory control, garbage collectors, resource managers existing in high level languages like Java, Python, etc, and working in runtime, opposite: the code can be very low level: assembler, C with manual control of all resources but safe enough bcs it was verified at "COMPILE" TIME and it was qualified as correct.

I will try to classify them all in the context of software development using AI, so maybe tables are not fully completed - check always the documentation of PA - they often add new features - example, I just checked the backend for Rocq (Coq) called "CertiCoq" and voila - it supports extraction to C subset (Clight) and... WebAssembly:

CertiRocq (formerly CertiCoq) is a compiler for Gallina, the specification language of the Rocq Prover. CertiRocq targets WebAssembly and Clight, a subset of the C language that can be compiled with any C compiler, including the CompCert verified compiler.

Supported languages

Notes on the table:

  • Proof assistant: primarily an interactive theorem prover, dependent type theory, higher-order logic system.
  • Verification language: primarily a programming language in which specifications and proofs are attached to executable programs.
  • Extraction: computational content is extracted from verified definitions, proofs, normally erasing logical, ghost material.
  • Code generation: verified, executable definitions are translated to another programming language.
  • Compilation: the system compiles its own language to executable code, rather than necessarily producing a human-oriented target-language program.
  • Proof, executable connection: how directly the generated executable implementation is connected to the object that was formally verified.

Classical extraction systems

Use-case: "I prove a theorem, define a constructive algorithm, and the system removes the proof-only material and gives me executable source code." - then the particularly relevant systems are:

System Classical extraction? Main targets
Rocq (Coq) YES OCaml, Haskell, Scheme
Agda YES-ish, compilation of computational content Haskell, JavaScript
Minlog YES Scheme
NuPRL YES Historically Lisp-oriented computational extraction

Rocq is particularly clear-cut: its extraction mechanism explicitly supports OCaml, Haskell and Scheme.

Why3 is similarly explicit: the command why3 extract generates OCaml, and its C driver can generate C for a supported subset of WhyML.

Specific runtime

The key distinction is between standalone generated code and code that depends on a language-specific runtime/library. Also, "no special runtime" does not necessarily mean "zero dependencies": e.g. generated C may use the C standard library or a small support library.

System Typical target Special runtime required? Generated code usable independently? Notes
Rocq/Coq OCaml, Haskell, Scheme - Usually no Rocq runtime Yes Extracted program is ordinary target-language code. It may depend on ordinary target libraries.
Lean 4 C/native + Lean runtime generally required No, not completely Lean's generated native code relies on Lean's runtime support for things such as memory management and runtime representations.
Isabelle/HOL SML, OCaml, Haskell, Scala - Generally no Isabelle runtime Yes Generated code is intended to be executable independently of Isabelle; target-language libraries/runtime still apply.
Agda Haskell, JavaScript + Target-language/runtime libraries Mostly yes Haskell output runs under GHC/Haskell runtime; JS output needs the normal JS environment and any generated support. No Agda theorem-prover runtime is normally required.
F* OCaml, F#, C, Rust - Depends on backend Often yes OCaml/F# can be ordinary target programs; C/Rust extraction can use generated/support libraries, depending on the F\*/KaRaMeL setup.
Why3 OCaml, C - Usually no Why3 runtime Yes One of the cleaner cases: extraction produces normal OCaml/C code. External libraries can of course be required.
Dafny C#, Java, JS, Go, Python, etc. + Yes, commonly Usually no Generated programs use Dafny runtime/support libraries for Dafny types and operations. This is one of the clearest examples of runtime-dependent generation.
ACL2/ATC C - Small/support runtime may be needed depending on features Largely yes ATC is specifically designed to generate C; generated code can be very close to conventional standalone C.
ACL2/ATJ Java ± ACL2-specific support may be required Not always Depends on which ACL2 constructs/features are translated.

Vale Assembly - No Vale runtime for the generated assembly itself Yes Designed specifically for low-level code; generated/verified routines can be incorporated into normal systems.

Also they can be grouped in this sense as:

Category Systems What you get
A. Truly independent extraction Rocq, Why3, Isabelle, Minlog, HOL4 Ordinary target-language source; no theorem-prover runtime is fundamentally part of the executable
B. Normal language compilation, proofs erased Verus, SPARK, Liquid Haskell, Vale The executable is essentially an ordinary Rust/Ada/Haskell/assembly program
C. Generated code + project/runtime support Dafny, Lean, some F_/Stainless configurations, ACL2/ATJ Generated source is usable, but some language/runtime support is normally carried along

The interesting cases

Dafny

This is the model you're probably thinking about: 

       Dafny source
            |
     <verification> ----> Z3, ...
            |
      Dafny compiler
            |
   .--------+--------.
   |        |        |           Dafny runtime
  C#      Java     Python ...          |
   |        |        |                 |
   `--------+--------'                 |
            |                          |
            +--------------------------'
            |
            v
        executable

That's an important distinction if your objective is "I want to give the generated source to somebody who doesn't have Dafny installed."

They generally don't need the Dafny compiler, but they may need the Dafny runtime/support package.

Rocq (Coq)

Rocq is much closer to what I'd call classical extraction: 

         Gallina
            |
    <theorems proving>
            |
       <extraction>
            |
    +-------+-------+
    |       |       |
    v       v       v
 OCaml   Haskell   Scheme
    |       |       |
    v       v       v
<compile w/o dependencies>

The resulting OCaml, for example, doesn't conceptually need Coq/Rocq to execute. The theorem prover is not part of the runtime architecture.

That is a major advantage if your goal is deployment.

Why3

Why3 is another particularly interesting one: 

              WhyML
                |
       +--------+--------+
       |                 |
  verification       extraction
       |                 |
  SMT solvers       +----+----+
                    |    |    |
                 OCaml   C   Java

The verification infrastructure is not needed to execute the resulting program. That makes it quite attractive for the: "Prove it here, deploy it somewhere completely unrelated." model.

Verus

Verus is perhaps even cleaner conceptually, because executable code is already Rust: 

fn verified_algorithm(...) -> ... {
    ...
}

----- alongside -----

spec fn ...
proof fn ...

The specification/proof portions are ghost material.

Conceptually: 

     Rust + proofs
          |
    Verus verifier
          |
          v
   erase ghost code
          |
          v
     ordinary Rust
          |
        rustc
          |
          v
    native binary

There is no Verus runtime that the deployed program needs. That's a very different architecture from Dafny.

Garbage collection

If your concern is not merely "special verifier runtime" but also "I want predictable systems code with no GC", the classification changes substantially.

System/target Typical GC? Suitable for GC-free systems code?
F* -> C No tracing GC required by C itself YES
Why3 -> C No YES
ACL2 -> C No YES
Verus -> Rust No tracing GC YES
Vale -> assembly No YES
SPARK -> Ada No tracing GC normally YES
Rocq -> OCaml Yes Usually no for hard real-time/GC-free requirements
Isabelle -> OCaml Yes Usually no
F* -> OCaml Yes Usually no
Rocq -> Haskell Yes Usually no
Agda -> Haskell Yes Usually no
Liquid Haskell Yes Usually no
Dafny -> C# Yes (.NET GC) Usually no
Dafny -> Java Yes (JVM GC) Usually no
Dafny -> Python Yes/managed memory No for this requirement
Lean native Runtime-managed Depends heavily on application, but not equivalent to bare C

Important distinction - 4 different questions:

  1. Does the target language normally have a garbage collector?
  2. Does the generated program require a GC?
  3. Does the generated program require a special runtime supplied by the verifier?
  4. Can the generated program use manual, ownership, region-based memory management instead?

These must not be conflated.

For example, C has no built-in GC: 

C program
    |
    +--> malloc/free
    |
    +--> custom allocator
    |
    +--> tracing GC library

And all 3 are perfectly legitimate C programs.

Therefore: "generates C" does not automatically means "does not use GC".

Also distinct "GC added by PA" and "GC pre-existing in the target language", e.g.: 

                 WhyML
                   |
              verification
                   |
          +--------+--------+
          |                 |
        OCaml               C
          |                 |
      OCaml GC      explicit C memory
          |                 |
          v                 v
      executable        executable

So, for Why3 -> OCaml you naturally get OCaml's GC, bcs you cannot remove the OCaml's GC from OCaml. But for extraction of C - you don't get any GC from Why3.

F* (Low*, KaRaMeL)

F* is one of the most interesting systems for this particular question.

Low* is explicitly designed to model C-like low-level computation. Its libraries model:

  • stack allocation
  • heap allocation
  • C arrays
  • machine integers
  • C memory
  • system-level C functionality

and KaRaMeL erases proofs before generating C (comparing to Why3 which can keep runtime asserts, if you need such ones).

Conceptually: 

F*/Low*
    |
    | proofs specifications
    |
    v
verification
    |
    | erase proofs
    |
    v
Low-level implementation
    |
    v
    C
    |
    +--> stack
    |
    +--> heap
    |
    +--> explicit allocation
    |
    +--> no GC required

This is fundamentally different from: 

high-level functional language
             |
             v
             C
             |
             v
    generated GC runtime

Low* is specifically trying to model the C memory behavior rather than hide it behind a tracing collector.

However, F* as a whole should not be labeled "no GC" bcs: 

F*
 |
 +--> OCaml backend       -> OCaml GC
 |
 +--> F# backend          -> .NET GC
 |
 +--> Low*/KaRaMeL -> C   -> can be GC-free
 |
 +--> other backends      -> depends

So F* can be treated as "backend-dependent" classification.

Dafny

Dafny is almost the opposite example. Supposing Dafny -> C++ it does not follow that you get "normal manual-memory C++". Dafny has its own runtime, support infrastructure, and generated C++ can depend on that infrastructure.

Therefore: 

  Dafny
   |
   v
  C++
   |
   +--> Dafny runtime
   |      |
   |      +--> runtime representations
   |      |
   |      +--> collections
   |      |
   |      +--> memory management
   |
   v
program

The generated C++ can therefore effectively have managed-memory semantics even though C++ itself has no mandatory tracing GC.

Isabelle/HOL

Isabelle's code generator produces SML, OCaml, Haskell and Scala.

Therefore the memory-management story is inherited largely from the target: 

Isabelle/HOL
 |
 +--> SML      -> SML runtime/GC
 |
 +--> OCaml    -> OCaml GC
 |
 +--> Haskell  -> GHC GC
 |
 +--> Scala    -> JVM GC

So Isabelle doesn't need an its own "Isabelle GC", but the generated program is certainly not necessarily GC-free.

Agda

Agda is similar: 

Agda
 |
 +--> Haskell     -> GHC GC
 |
 +--> JavaScript  -> JS engine GC

Lean

Lean is different.

Lean's executable model includes a runtime system, and its compiler targets native code through its compilation infrastructure.

A more accurate model for Lean is: 

    Lean
     |
     v
Lean compiler
     |
     v
native code
     |
     +--> Lean runtime
              |
              +--> runtime representations
              |
              +--> memory management
              |
              +--> GC/runtime machinery

ACL2/ATC

ACL2's ATC is interesting because it generates C and is explicitly designed as a proof-generating C code generator.

The conceptual model is: 

       ACL2
        |
        | proof
        |
        v
       ATC
        |
        v
        C
        |
        v
ordinary C compiler

ATC is much closer to: "generate C that follows the proved semantics" than to: "generate C plus a large managed-language runtime".

So GC is not normally intrinsic for ACL2.

Of course, nothing prevents the generated C program from linking against a GC library if the application requires one.

Vale

Vale operates at a much lower level - Vale is a DSL/toolchain for verified ASSEMBLY (ARM, x86?) for F* and Dafny, see more. The project today does not look as too alive though.

Its generated/verified code can be incorporated into systems software without a mandatory tracing GC.

But, just as with C or assembly generally: 

"no mandatory GC"
       !=
"GC impossible"

You can implement a GC in assembly.

The relevant question is whether the Vale-generated code requires one. Normally, no.

HOL4

HOL4 can generate SML, so its extracted code uses GC of SML (not specially generated by HOL4).

A better overall classification

                       GENERATED PROGRAM
                              |
             +----------------+----------------+
             |                                 |
          managed                          explicit
             |                               memory
             |                                 |
       +-----+-----+                    +------+------+
       |           |                    |             |

runtime support

So "GC or no GC" is not the whole story.

For systems programming, this it a richer classification:

The surprising case: C + verified GC

This is why the CertiCoq ecosystem is particularly interesting.

It is possible to have: 

               Rocq
                 |
           proof/program
                 |
             CertiCoq
                 |
                 v
             generated C
                 |
        +--------+--------+
        |                 |
   application        verified GC
        |                 |
        +--------+--------+
                 |
                 v
           machine code

So there is nothing contradictory about: 

      "C code"
         +
"garbage collection"
         +
"formally verified"

C doesn't prohibit GC; it simply doesn't provide one as part of the language.

Bottom line

So, yes: there absolutely are provers/formal-verification systems where the generated language is C/C++ but the resulting program can still have a garbage collector.

The cleanest conceptual distinction is: 

                   C/C++
                     |
          +----------+----------+
          |                     |
       GC-based             GC-free
          |                     |
   runtime/collector       malloc/free
          |                 ownership
          |                  regions
          |                  arenas
          |                     |
   CertiCoq-style         Low*/KaRaMeL
   / Dafny-style             Why3/C
                            ACL2/ATC

CertiRocq-generated code normally relies on a CertiRocq runtime, and that runtime includes a generational garbage collector.
