* The idea

Very briefly, because today everyone knows what it is. The idea is that in mathematics, logic,
you prove theorems but the idea is that it can be done "automatically", well, not absolutely
automatically but using a computer: see [[https://en.wikipedia.org/wiki/Automated_theorem_proving][Automated theorem proving]]. And this allows to
mathematicians to state proving more formal, and more strict, "provable". But it is for math.

The idea is that the same approach can be used for proving of some properties of software.

* Why it matters in the epoch of AI

People see that theorem provers become more and more popular. Why?

1. They become more mature and better
2. The cost of "error" becomes big (hackers, buggy code, etc)
3. Their number is increasing
4. "Buzz-word"
5. AI effect

What is "AI effect"? There is now a fairly substantial ecosystem where an AI proposes a
mathematical statement/proof, and a theorem prover such as Lean acts as the trusted
checker. There are also projects where the prover catches errors in the AI-generated/formalized
result itself. Examples (however, more close is ProofNet-Verifided):

- [[https://github.com/marcusm117/ProofNet-Verified][ProofNet-Verified]]: a benchmark where natural-language undergraduate mathematics
  is translated into Lean
- [[https://leandojo.org/leandojo][LeanDojo]] / [[https://github.com/lean-dojo/ReProver][ReProver]]: LLM proposes proofs, Lean verifies them
- [[https://github.com/Kripner/openprover][OpenProver]]: workers generate mathematical ideas/proof steps, while verification is delegated
  to Lean
- [[https://github.com/facebookresearch/miniF2F][MiniF2F]]: math problem is proved by LLM then LEAN check it
- [[https://paperswithlean.com/paper/2606.20068.html][Process-Verified RL]]: a newer direction, instead of merely asking: "Did the AI eventually
  produce a correct proof?" the researchers use Lean to provide fine-grained feedback during
  the proof process. LLM generates several steps, LEAN reject some of them

So, the collaboration between theorem provers and AI/LLM today looks as:

| Use                               | AI does                                    | Theorem prover does                                             |
|-----------------------------------+--------------------------------------------+-----------------------------------------------------------------|
| Proof generation                  | Invents a proof                            | Checks it                                                       |
| Proof correction                  | Proposes another proof after failure       | Identifies invalid steps                                        |
| Result/formalization verification | Translates a human result into formal math | Determines whether the formal statement/proof is actually valid |

So, one of the scenario is:

       |   LLM / Agent     ‖

                |
        .-------+--------.
        |                |
      VALID           INVALID
        |                |
        v                v
   accept result    feedback to AI
                         |
                         `--> revise
#+end_example

* Why Why3

[[https://why3.org/][Why3]] is such a tool: you describe your "model" (of a program) then its properties then you
prove them. If successfully then your software (different pieces of your code) is safe (as you
described "safety" with those properties), else - you think about your code something, but it
is something else.

#+begin_quote
Why3 is a platform for deductive program verification. It provides a rich language for
specification and programming, called WhyML, and relies on external theorem provers, both
automated and interactive, to discharge verification conditions.

-- https://why3.org/
#+end_quote

* Comparison of tools for computer science

Instead of big comparison, I will show only my impressions: *Why3* is good for verification of
algorithms and existing software. It's syntax and semantic are simple mostly. Also it supports
extraction. You can verify C/C++ programs with it, but it is not so low-level and it's more oriented
on computer science, but again - it is possible sure but it is not its goal, purpose. Also it is
used for verification of distributed architectures and algorithms.

*F-star* is very close to Why3, the same [[https://www.inria.fr/en][National institute Inria]] is involved, it is ML-based too,
it supports the same proving features, but additionally it supports dependent types, effects are
more obvious/explicit, refinement types are explicit (connected to a type, not to a contract), also
it is better (maybe, not 100% sure) in code extraction, and more important - it supports LOW-LEVEL
VERIFICATION: C, assembler.

If to compare theorem provers in the context of LOW-LEVEL safe programming (think about OS kernels,
bare-metal, low-level cryptography, assembler, chips firmware, etc) F* and VST/Rocq have serious
low-level stories, while Why3 and Dafny are primarily deductive-verification frameworks/languages
whose low-level support is more indirect. current F* has moved toward Pulse as its
imperative/separation-logic language; the older Low* sublanguage has been removed from F* releases,
although the Low* libraries/tooling remain relevant to existing projects.

- Existing C code: VST/Rocq is the most directly purpose-built of these.
- Writing new low-level C from scratch: F*/Pulse + KaRaMeL is extremely compelling.
- Handwritten assembly: F* + Vale is the standout here; VST can reason about CompCert's assembly
  semantics, but VST itself is fundamentally a C verification framework.
- Mostly ordinary imperative code with some low-level flavor: Dafny is much easier to get started
  with, and Vale can take it surprisingly far into assembly.
- SMT-heavy deductive verification, particularly if you want many automated provers: Why3 is
  excellent, but it is not the tool I'd reach for first for machine-level C/assembly.

Why3 micro-C is mostly for teaching (it's tiny subset of C).

** VST/Rocq and "low-level" programming

VST / Rocq is very mature and solid here - low-level C is it's home. It was used for verification of
SHA-256, HMAC, mbedTLS HMAC-DRBG, TweetNaCl / Curve25519 cryptography, garbage collection, graph
algorithms, concurrent messaging, an HTTP key-value server, differential-equation solvers, and
Reed–Solomon coding, etc. Canonical VST case study is [[https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/beringer][verification of OpenSSL HMAC + SHA-256]]. The
work also connected the C-level proof to CompCert's verified compilation to assembly. The authors
describe it as combining source-program correctness, compiler correctness, and
cryptographic-security proofs without gaps at the specification interfaces. Additionally to
cryptography VST is widely used in memory work verification, it supports:

- pointers
- aliasing
- ownership
- memory invariants
- low-level data structures
- allocators
- and so on...

Also it is used for numerical scientific C, [[https://www.cs.princeton.edu/~appel/papers/][a lot of examples]], [[https://blog.poisson.chat/posts/2019-01-14-cpp19-from-c-to-itrees.html][network programming verification]]

See [[https://vst.cs.princeton.edu/][more about VST]].

** F star and "low-level" programming

F* has an unusually strong real-world systems/security track record, arguably more concentrated
around cryptography, networking, and verified low-level code than VST's.

The important distinction is that many of the projects below are part of the broader Project Everest
ecosystem: F* is the specification/proof language, while tools such as KaRaMeL and Vale connect the
proofs to C and assembly. Famous project where the code was verified and extracted is HACL*:

HACL* is a collection of verified cryptographic primitives implemented in F*, with extraction to
C. It includes algorithms such as:

- Curve25519
- Ed25519
- AES
- SHA-2
- ChaCha20
- Poly1305
- various hash/MAC constructions

It was extracted to C and has been integrated into real software including Firefox, Linux, and
WireGuard. Another project created with F* is EverCrypt:

EverCrypt is a larger cryptographic provider built on the Everest verification technology. It
combines verified implementations of cryptographic primitives with:

- algorithm agility,
- hardware acceleration,
- architecture-specific implementations,
- runtime selection,
- *CONSTANT-TIME GUARANTEES!*

Another project: Vale (verified cryptographic assembly). Vale is designed specifically for verifying
low-level assembly. It has been used to verify optimized cryptographic implementations, including
assembly for:

- AES-GCM
- ChaCha20
- Poly1305
- Curve25519-related operations
- other cryptographic primitives

Vale supports x86/x64 and ARM-family architectures, and its verification is integrated with F* and
Dafny.

Low*/Pulse was designed to give F* programs a C-like computational model:

- mutable buffers
- pointers
- arrays
- structs
- machine integers
- stack/heap memory
- explicit effects
- memory safety.

KaRaMeL then translates verified Low* programs into C.

* How much does this save you from bugs?

After proof, your code may still contain errors. This is due to:

- you did not enumerate all important properties, you missed something
- there are "not logical" bugs, for example, error (additive, for example) is too large, ie, the
  software is not accurate enough in numerical calculation. But, this also CAN BE VERIFIED WITH
  THEOREM PROVERS!
- bugs happen outside of verified code - in the effectful world (API, network, libraries,
  OS...). BUT SOME PROVERS CAN REASON ABOUT EFFECTS TOO.
- serious performance problems. But SOME PROVERS CAN WORK WITH THIS EVEN.
- policy related errors: bad UX, strange behavior on errors, weird understanding of the domain
  problems...
- bad design
- sometimes even proof can be not good enough (the probability of this is low: automatic
  verification checks the correctness of the proof)

After proof usually you get:

- More correct code (or even significantly more correct, sometimes - code without bugs at all)
- You better understand your code and its corner cases, features, its pros and cons

* Setup of Why3 on Linux

Why3 can be installed from your distribution package manager. Also it comes with its default
SMT solvers. Currently, it is CVC4, but it is not so good, and you can hit problems with
it. So, I'd recommend to install Z3 SMT solver from the package manager and then to configure
Why3 to "see" it:

#+begin_example
$ why3 config detect
$ why3 config list-provers   # and you should see Z3 now in the list
# After it use can use z3 during prooving woth "-P z3" option
#+end_example

** My makefile

#+begin_src makefile :eval no :exports both
set -o pipefail
[ -z "$1" ] && { echo 'Arg1: path to .mlw file' ; exit 1; }
[ "${WHY3_SPLITVC+x}" ] && split_opt='-a split_vc'
why3 prove -P ${WHY3_PROVER:-z3} -t ${WHY3_TIMEOUT:-10} "$1" $split_opt $WHY3_OPTS | tee _"$1".proven
echo '-----------------------------------------------------'
grep -P -B 2 '^Prover result is: (?!Valid)' _"$1".proven | tee _"$1".error
[ $? -eq 0 ] && { echo; echo '*** ERROR: NOT PROVEN! ***'; exit 1; } || exit 0
#+end_src

#+begin_src sh :eval no :exports both

* Why proving is "metaprogramming"

There is such a term - [[https://en.wikipedia.org/wiki/Metaprogramming][metaprogramming]] and logic "lives between liens of code" or on the top of
it, not participating in computation but checking/verifying it: *it is a program about program*.

* Program and logic: computational and logic code

All WhyML code is split to 2 pies - WORLDS: a program (computational) "world" and logic
"world". And... there are constructions living in both "worlds".

- *Program/computational WhyML code* — code that describes computation: functions, mutable
  state, references, loops, exceptions, I/O, etc. It is executed or compiled.
- *Logical code* — specifications and mathematical objects used to reason about the program:
  predicates, propositions, lemmas, axioms, pure functions, mathematical types, etc. It is not
  executed as program code; it is translated into proof obligations for automated/theorem
  provers.

So, logical world (code) is metaprogramming. Computational (or program) world (code) is your
program. Also it matters in extraction phase - logical code will not generate Ocaml, C output,
in short.

* Solver, SMT, SAT...

About SMT and SAT in [[https://en.wikipedia.org/wiki/Satisfiability_modulo_theories][Wikipedia]].

** SAT

SAT solves boolean "satisfiability" answering the question: "Can I assign true/false to these
boolean variables so that the whole formula becomes true?", example:

#+begin_example
Input formula :            (A OR B) AND (NOT A OR C)

A SAT solver might find :  A = false
                           B = true
                           C = false

                           
#+end_example

It's kind of utility helper in the world of automatic logic. SAT works fundamentally with
~true/false~, ~AND, OR, NOT~... It is something like "constraint programming over boolean
domain".

#+begin_quote
A SAT solver doesn't inherently understand things like:

x + 1 > x

because ~x~ there isn't a boolean variable.
#+end_quote

** SMT

SMT means "Satisfiability Modulo Theories", it answers the question: "Is there an assignment
that makes this formula true?", but SMT allows variables from particular mathematical theories.

For example, integer arithmetic:

#+begin_example
Input :                   x: Int
                          y: Int
                          x > 10
                          y = x + 5
                          y < 20

                          
SMT solver might find :   x = 11
                          y = 16
#+end_example

SMT works in domains:

- integers and real numbers
- arithmetic
- arrays
- bit-vectors
- equality
- uninterpreted functions
- sometimes strings (CVC 4 (strings), etc), floating point, etc.

Modern SMT solvers combine: Boolean reasoning of SAT with its own standard Theory reasoning,
i.e., SAT today is usually embedded part of SMT.

Why3, Dafny, F*, etc, delegate "simple" work to SMT. Rocq, LEAN - do not (they can do all work
by self, but they allow to use external solvers).

First, we see on ~1~ the declaration of the function ~calc_diffs~ which has 2 arguments: an
array of integers and a boolean, and it returns an array of integers. Also it has one
postcondition on line ~2~ (see ~ensures {..}~), it could have preconditions too...

postcondition on ~2~ says: there are 2 statements - they are formed as ~first AND second~
("and" is ~/\~):

1. ~(length ps = 0 -> length result = 0)~
   If the length of the argument ~ps~ is 0 then the result of the function will have a length 0 too
2. ~(length ps > 0 -> length result = length ps - 1)~
   If the argument ~ps~ is not empty then the length of the result is lesser of ~ps~ by 1.

Why3 will check the code of the function and will prove or refute such statements, you can do
it by self:

1. initially the loop variable ~i~ is 0
2. it's bound is ~length ps - 1~ (on ~12~)

Why3 does it automatically, for you.

*These properties (postconditions in the case) are important: you know what to expect from the
function.*

Also they will be used in proving of other pieces of the code, they are "a contract", and when
it is called somewhere, Why3 can reason about its result.

Types matter - they are also controlled by Why3 - if an expression violates the declared type,
it is also reported as an error, obviously.

Inside ~while~ loop we see ~invariant~ and ~variant~ expressions. "Invariant" describes
something that does not change - it is checked too also this knowledge is remembered as a fact
and can be used later for further proving. These 2 invariant expressions do state:

- ~invariant { 0 <= !i <= length ps - 1 }~
  we guarantee inside the loop that ~i~ is always in this diapason, i.e., ~[0..length ps-1]~
- ~invariant { !i <= length diffs }~
  also we guarantee that ~i~ is always lesser or equal to the length of the array ~diffs~

Invariants also can help proving of other claims - without them some claims will not be proven.

Little note: ~!~ in the front of ~i~ is "dereferencing" like "*" in C - "take the content of
the reference" - to be mutable we declared ~i~ as reference.

OK, also we see "variant". The idea of a variant expression is more interesting: it guarantees
that something is "decreasing" - it states "what" does it. Why do we need it? Usually it is
needed in:

- ~while~-loop (in ~for~-loop it is obvious, so it is redundant and syntactically denied)
- in recursive functions

"Variants" state that something becomes smaller and smaller and this thing is known as
something having "ZERO" - the smallest form, it cannot become "smaller" and it guarantees Why3
that looping construction will complete (it is not forever-running, it will terminate) - most
looping constructions are such ones. Sure, exceptions of this are supported (~diverges~
keyword). OK, so here: ~variant { length ps - 1 - !i }~ we say that this "thing" (expression)
becomes smaller and smaller, considering the length of ~ps~ is 3:

| !i | 3 - 1 - !i (ie, length ps - 1 - !i) | treating                    |
|----+-------------------------------------+-----------------------------|
|  0 |                                   2 | search further...           |
|  1 |                                   1 | search further...           |
|  2 |                                   0 | 0 = SMALLEST, STOP IS HERE! |

Theorem provers know: if we hit the smallest "thing" (and it checks the code sure, that it's
true), then we reach the end of the looping. It means - no infinite loop here.

*Variant expression just focus Why3 what "thing" to check for termination - the decrease of it
is checked by Why3 itself*

Such "things" can be integers, lists (reaching of ~Nil~ - the empty tail), etc.

And *these "variants" and "invariants" give knowledge about looping constructions: what is true
on every step/iteration, what does guarantee that the end of the loop or recursion.*

*** Case 1: l = []

Why3 enters ~| Nil -> ()~ - unit, so, NO RECURSIVE CALL: EXECUTE NOTHING, PRODUCE ~()~.

*But Why3 still must verify the CONTRACT (pre/postconditions)*

- Precondition ~P [] n /\ 0 <= x < n~.
- Why3 automatically unfold ~P~, knowing its definition, from that definition it found that
  when ~l~ is ~Nil~, the result is true: ~P Nil n -> true~, so now: ~true /\ 0 <= x < n~.
- So, THIS IS THE PRECONDITION (!!!).
- Postcondition is ~P (l ++ [x]) n~, currently ~l = []~, so the postcondition is ~P ([] ++ [x])
  n~. Again, Why3 must still prove: PRE -> POST.
- Why3 knows the definition of ~++~ (see the module ~Append~ in
  ~/usr/share/why3/stdlib/list.mlw~). So, the result of ~[] + some_list -> some_list~ and
  the postcondition becomes ~P [x] n~.
- To prove it Why3 again goes to ~P~ definition and unfolds ~P [x]~: it is ~0 <= x < n /\ P []~.
- ~P [] n~ is true, again. So, the postcondition is ~0 <= x < n /\ true~.
- Now Why3 HAS COMPLETELY UNFOLDED POSTCONDITION TOO. They are:
  PRE: ~true /\ 0 <= x < n~. POST: ~0 <= x < n /\ true~. Tautology, so PRE -> POST is proven!!!

Why3 always must prove PRE -> POST, but sometimes also it should execute code, sometimes - no.

*** Case 2: l = [y] and more

Now Why3 enters ~| Cons _ r -> foo r x n~ (~foo~ here is the recursive call of the lemma).
~r = []~, cos ~l = y :: []~. Why3 walks into recursive call:

- Precondition now is ~P [y] n /\ 0 <= x < n~.
- Why3 unfold ~P [y] n~ again: ~0 <= y < n /\ P [] n~ (as we remember ~P [] n~ is true)
- and so on... Recursive structure of the verification look as:

#+end_example

This is complex bounds check because it should check that all items in ~ranges_arr~ array do not
violate ~[0..|isovalues_arr|)~. Also Why3 checks that ~irange~ is in ~0..|ranges_arr|~.

* Hoare triples and difference with traditional asserts

https://en.wikipedia.org/wiki/Hoare_logic#Hoare_triple :

A Hoare triple is of the form ~{P} C {Q}~, where ~P~ and ~Q~ are assertions and ~C~ is a
command. ~P~ is named the precondition and ~Q~ the postcondition: when the precondition is met,
executing the command establishes the postcondition.

So, a program can be split to pieces with asserts:

#+begin_example
            code...
            code...
  /some state of the program\   P: assert(..)
  \ treated as precondition /
            code...             C
            code...
  /some state of the program\   Q: assert(..)
  \ treated as postcondition/
            . . .          
#+end_example

The difference is that usual asserts is C, Python, etc *are checked in runtime* while asserts in
Why3 (and similar) are verified, without to run the program! BUT... Why3 support so called RAC:
runtime assertion checking and Why3 has a lot of options for RAC. It allows to keep assertions at
runtime too (in extracted code).

OK, so, Python, C assertions live only in so called "instrumental build", and they are removed in
release builds. But they should not be removed from the code, they are not only for verification in
runtime, - they also are DOCUMENTATION, CONTRACTS for a programmer who can understand the behavior
of the program better - they are like "monitors" guarantying that here, in this point the state is
such one.

* The difference with Rocq, LEAN - dark side

Sometimes verification fails with errors "timeout" and "out of memory".

*IT IS TRUE FOR ALL THEOREM PROVERS*.

"Out of memory" and timeout usually mean "the generated verification problem became too hard for the
prover," not necessarily that the proposition is false or that Why3 is stuck executing your program.

- A timeout says: "I haven't finished."
- OOM says something closer to: "I generated/constructed too much state."

And even 1, very small change of the WhyML code can lead to timeout or OOM. Their debugging in very
difficult. 2 mathematically equivalent formulations can have radically different performance. A
timeout does not mean "the theorem is difficult". Sometimes it can be even obvious to a human (see
above my axiom-workaround).

This is why Why3 verification often involves proof engineering:

- choose good invariants
- introduce lemmas
- control definitions
- split goals
- avoid unnecessary quantifiers
- provide intermediate facts
- choose appropriate triggers/provers
- sometimes explicitly instantiate lemmas

Proof engineer not changing the mathematics; he/she changes *the shape of the problem* presented to
the automated prover.

The control of proving "route" in Rocq, LEAN is more "manual" (it can be automatic, but it can be
very manual) and there OOM, timeouts happen too, but they allow more control to avoid them - if you
know how to achieve it.
