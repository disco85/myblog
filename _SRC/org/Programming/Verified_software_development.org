* Use cases of proof assistants

All use cases can be grouped to:

1. formalizing mathematics, mathematical foundations, physics, economics, etc
2. verification of algorithms, models, specifications, software, hardware, certification, etc
3. control of AI results, improvement of AI results, etc
4. software development, hardware development, etc 

4-th - software development is in the focus of this article. It is not just proving,
verifying of some properties of some theories, models, algorithms, etc - IT IS CREATION OF
SOFTWARE. Yes, theorem provers, proof assistants (lets call them PA) can be used
to... WRITE SOFTWARE... and they are already used today -

you can start with [[https://www.youtube.com/watch?v=c5LOYzZx-0c]["The Best New Programming Language is a Proof Assistant"]].

How does it happen? Mostly - via compilation and extraction:

#+begin_example
                  special language
 (sometimes allows traditional programming language)
                         |
                         v
                  proof assistant
                developing software
                         |
           .-------------+-------------.
           |                           |
           v                           v
      compilation                  extraction
          to                           to
      executable                some programming
                                    language
#+end_example

Some of PA support compilation, some - extraction, some - both. Some of them can execute
the PA code directly (eg, Why3), some of them understand more than 1 input language,
including traditional programming languages (Why3 is such PA!).

The ultimate idea is that you get very safe, verified software which is safe not bcs it
uses runtime mechanisms like automatic memory control, garbage collectors, resource
managers existing in high level languages like Java, Python, etc, and working in runtime,
opposite: *the code can be very low level: assembler, C with manual control of all
resources but safe enough bcs it was verified at "COMPILE" TIME and it was qualified as
correct*.

I will try to classify them all in the context of /software development/ using AI, so
maybe tables are not fully completed - check always the documentation of PA - they often
add new features.

* Supported languages

Notes on the table:

- Proof assistant: primarily an interactive theorem prover, dependent type theory,
  higher-order logic system.
- Verification language: primarily a programming language in which specifications and
  proofs are attached to executable programs.
- Extraction: computational content is extracted from verified definitions, proofs,
  normally erasing logical, ghost material.
- Code generation: verified, executable definitions are translated to another programming
  language.
- Compilation: the system compiles its own language to executable code, rather than
  necessarily producing a human-oriented target-language program.
- Proof, executable connection: how directly the generated executable implementation is
  connected to the object that was formally verified.

* Classical extraction systems

Use-case: "I prove a theorem, define a constructive algorithm, and the system removes the proof-only
material and gives me executable source code." - then the particularly relevant systems are:

| System       | Classical extraction?                            | Main targets                                        |
|--------------+--------------------------------------------------+-----------------------------------------------------|
| Rocq (Coq)   | YES                                              | OCaml, Haskell, Scheme                              |
| Agda         | YES-ish, compilation of computational content    | Haskell, JavaScript                                 |
| Minlog       | YES                                              | Scheme                                              |
| NuPRL        | YES                                              | Historically Lisp-oriented computational extraction |
| Isabelle/HOL | Code generation rather than Coq-style extraction | SML, OCaml, Haskell, Scala                          |
| Lean         | Compilation rather than classical extraction     | Native executable via compiler or C backend         |
| F*           | Extraction, code generation                      | OCaml, F#, C, Rust through ecosystem                |
| Why3         | Program extraction                               | OCaml, C                                            |

Rocq is particularly clear-cut: its extraction mechanism explicitly supports OCaml, Haskell and Scheme.

Why3 is similarly explicit: the command =why3 extract= generates OCaml, and its C driver
can generate C for a supported subset of WhyML.

** Verified output vs verified source

| Level | Meaning                                              | Examples                                       |
|-------+------------------------------------------------------+------------------------------------------------|
| L0    | No executable-code generation                        | Viper-like verification infrastructure         |
| L1    | Compile verified source normally                     | Verus, SPARK, Liquid Haskell                   |
| L2    | Generate executable source from verified definitions | Dafny, Stainless, Isabelle, Why3               |
| L3    | Proof, program extraction                            | Rocq, Minlog, constructive type-theory systems |
| L4    | Proof-producing low-level generation                 | ACL2, ATC, parts of F* with KaRaMeL/Vale       |

* Specific runtime

The key distinction is between **standalone generated code** and code that depends on a
**language-specific runtime/library**. Also, "no special runtime" does not necessarily
mean "zero dependencies": e.g. generated C may use the C standard library or a small
support library.

| System              | Typical target                 | Special runtime required?                                   | Generated code usable independently? | Notes                                                                                                                                                                    |
|---------------------+--------------------------------+-------------------------------------------------------------+--------------------------------------+--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Rocq / Coq**      | OCaml, Haskell, Scheme         | - Usually **no Rocq runtime**                               | **Yes**                              | Extracted program is ordinary target-language code. It may depend on ordinary target libraries.                                                                          |
| **Lean 4**          | C / native                     | + **Lean runtime** generally required                       | **No, not completely**               | Lean's generated native code relies on Lean's runtime support for things such as memory management and runtime representations.                                          |
| **Isabelle/HOL**    | SML, OCaml, Haskell, Scala     | - Generally **no Isabelle runtime**                         | **Yes**                              | Generated code is intended to be executable independently of Isabelle; target-language libraries/runtime still apply.                                                    |
| **Agda**            | Haskell, JavaScript            | + **Target-language/runtime libraries**                     | **Mostly yes**                       | Haskell output runs under GHC/Haskell runtime; JS output needs the normal JS environment and any generated support. No Agda theorem-prover runtime is normally required. |
| **F***              | OCaml, F#, C, Rust             | - **Depends on backend**                                    | **Often yes**                        | OCaml/F# can be ordinary target programs; C/Rust extraction can use generated/support libraries, depending on the F\*/KaRaMeL setup.                                     |
| **Why3**            | OCaml, C                       | - Usually **no Why3 runtime**                               | **Yes**                              | One of the cleaner cases: extraction produces normal OCaml/C code. External libraries can of course be required.                                                         |
| **Dafny**           | C#, Java, JS, Go, Python, etc. | + **Yes, commonly**                                         | **Usually no**                       | Generated programs use Dafny runtime/support libraries for Dafny types and operations. This is one of the clearest examples of runtime-dependent generation.             |
| **ACL2 / ATC**      | C                              | - Small/support runtime may be needed depending on features | **Largely yes**                      | ATC is specifically designed to generate C; generated code can be very close to conventional standalone C.                                                               |
| **ACL2 / ATJ**      | Java                           | ± ACL2-specific support may be required                     | **Not always**                       | Depends on which ACL2 constructs/features are translated.                                                                                                                |
| **Stainless**       | Scala, C                       | ± Backend/runtime support depends on generated features     | **Often yes**                        | Generated Scala is normal Scala; GenC can require Stainless support/runtime for some constructs.                                                                         |
| **Verus**           | Rust                           | - **No Verus runtime**                                      | **Yes**                              | `spec`/`proof`/ghost material is erased; executable Rust is compiled normally. This is a particularly clean model.                                                       |
| **SPARK**           | Ada                            | - **No SPARK runtime in the conceptual sense**              | **Yes**                              | SPARK is a subset/methodology over Ada. Verified Ada is compiled using normal Ada toolchains/runtime as appropriate.                                                     |
| **Liquid Haskell**  | Haskell                        | - **No Liquid Haskell runtime**                             | **Yes**                              | Refinements disappear; resulting program is ordinary Haskell.                                                                                                            |
| **Vale**            | Assembly                       | - **No Vale runtime for the generated assembly itself**     | **Yes**                              | Designed specifically for low-level code; generated/verified routines can be incorporated into normal systems.                                                           |
| **K Framework**     | Depends on backend             | ± **Usually backend-specific**                              | **Depends**                          | K is primarily semantics/execution/verification infrastructure rather than a simple extraction pipeline.                                                                 |
| **Event-B / Rodin** | Various                        | ± **Depends on code-generation toolchain**                  | **Depends**                          | Refinement/code-generation approach rather than classical proof extraction.                                                                                              |
| **B Method**        | Ada, C, etc.                   | ± **Depends on toolchain**                                  | **Usually yes**                      | Generated implementation can become ordinary target-language code.                                                                                                       |
| **PVS**             | Various                        | - **Not primarily an extraction system**                    | **Depends**                          | Code generation is not its central use case.                                                                                                                             |
| **HOL4**            | SML                            | - **No HOL runtime normally required**                      | **Yes**                              | Generated SML can be compiled/executed as ordinary SML.                                                                                                                  |
| **Minlog**          | Scheme                         | - **No Minlog runtime in the classical model**              | **Yes**                              | Constructive proof → extracted Scheme program.                                                                                                                           |
| **NuPRL**           | Lisp-oriented                  | ± Historically implementation-dependent                     | **Depends**                          | More of a historical/academic example of computational extraction.                                                                                                       |

Also they can be grouped in this sense as:

| Category                                      | Systems                                                 | What you get                                                                                       |
|-----------------------------------------------+---------------------------------------------------------+----------------------------------------------------------------------------------------------------|
| A. Truly independent extraction               | Rocq, Why3, Isabelle, Minlog, HOL4                      | Ordinary target-language source; no theorem-prover runtime is fundamentally part of the executable |
| B. Normal language compilation, proofs erased | Verus, SPARK, Liquid Haskell, Vale                      | The executable is essentially an ordinary Rust/Ada/Haskell/assembly program                        |
| C. Generated code + project/runtime support   | Dafny, Lean, some F_/Stainless configurations, ACL2/ATJ | Generated source is usable, but some language/runtime support is normally carried along            |
| D. Backend/toolchain dependent                | K, Event-B, B, PVS                                      | Whether the final artifact is standalone depends substantially on the particular backend/toolchain |

** The interesting cases

*** 1. Dafny

This is the model you're probably thinking about:

#+begin_example
       Dafny source
            |
     <verification> ----> Z3, ...
            |
      Dafny compiler
            |
   .--------+--------.
   |        |        |           Dafny runtime
  C#      Java     Python ...          |
   |        |        |                 |
   `--------+--------'                 |
            |                          |
            +--------------------------'
            |
            v
        executable
#+end_example

That's an important distinction if your objective is **"I want to give the generated
source to somebody who doesn't have Dafny installed."**

They generally don't need the Dafny compiler, but they may need the **Dafny runtime/support package**.

*** 2. Rocq (Coq)

Rocq is much closer to what I'd call classical _extraction_:

#+begin_example
         Gallina
            |
    <theorems proving>
            |
       <extraction>
            |
    +-------+-------+
    |       |       |
    v       v       v
 OCaml   Haskell   Scheme
    |       |       |
    v       v       v
<compile w/o dependencies>
#+end_example

The resulting OCaml, for example, doesn't conceptually need Coq/Rocq to execute. The
theorem prover is **not part of the runtime architecture**.

That is a major advantage if your goal is deployment.

*** 3. Why3

Why3 is another particularly interesting one:

#+begin_example
              WhyML
                |
       +--------+--------+
       |                 |
  verification       extraction
       |                 |
  SMT solvers       +----+----+
                    |    |    |
                 OCaml   C   Java
#+end_example

The verification infrastructure is not needed to execute the resulting program. That makes
it quite attractive for the: *"Prove it here, deploy it somewhere completely unrelated."* model.

*** 4. Verus

Verus is perhaps even cleaner conceptually, because executable code is **already Rust**:

#+begin_example
fn verified_algorithm(...) -> ... {
    ...
}

----- alongside -----

spec fn ...
proof fn ...
#+end_example

The specification/proof portions are ghost material.

Conceptually:

#+begin_example
     Rust + proofs
          |
    Verus verifier
          |
          v
   erase ghost code
          |
          v
     ordinary Rust
          |
        rustc
          |
          v
    native binary
#+end_example

There is **no Verus runtime** that the deployed program needs. That's a very different architecture from Dafny.

* Garbage collection

If your concern is not merely "special verifier runtime" but also "I want predictable systems code with no GC", the classification changes substantially.

| System / target   | Typical GC?                        | Suitable for GC-free systems code?                           |
|-------------------+------------------------------------+--------------------------------------------------------------|
| F* -> C           | No tracing GC required by C itself | YES                                                          |
| Why3 -> C         | No                                 | YES                                                          |
| ACL2 -> C         | No                                 | YES                                                          |
| Verus -> Rust     | No tracing GC                      | YES                                                          |
| Vale -> assembly  | No                                 | YES                                                          |
| SPARK -> Ada      | No tracing GC normally             | YES                                                          |
| Rocq -> OCaml     | Yes                                | Usually no for hard real-time / GC-free requirements         |
| Isabelle -> OCaml | Yes                                | Usually no                                                   |
| F* -> OCaml       | Yes                                | Usually no                                                   |
| Rocq -> Haskell   | Yes                                | Usually no                                                   |
| Agda -> Haskell   | Yes                                | Usually no                                                   |
| Liquid Haskell    | Yes                                | Usually no                                                   |
| Dafny -> C#       | Yes (.NET GC)                      | Usually no                                                   |
| Dafny -> Java     | Yes (JVM GC)                       | Usually no                                                   |
| Dafny -> Python   | Yes / managed memory               | No for this requirement                                      |
| Lean native       | Runtime-managed                    | Depends heavily on application, but not equivalent to bare C |

Important distinction - 4 different questions:

1. Does the target language normally have a garbage collector?
2. Does the generated program require a GC?
3. Does the generated program require a special runtime supplied by the verifier?
4. Can the generated program use manual, ownership, region-based memory management instead?

These must not be conflated.

For example, C has no built-in GC:

#+begin_example
C program
    |
    +--> malloc/free
    |
    +--> custom allocator
    |
    +--> tracing GC library
#+end_example

And all 3 are perfectly legitimate C programs.

Therefore: "generates C" does not automatically means "does not use GC".

Also distinct "GC added by PA" and "GC pre-existing in the target language", e.g.:

#+begin_example
                 WhyML
                   |
              verification
                   |
          +--------+--------+
          |                 |
        OCaml               C
          |                 |
      OCaml GC      explicit C memory
          |                 |
          v                 v
      executable        executable
#+end_example

So, for Why3 -> OCaml you naturally get OCaml's GC, bcs you cannot remove the OCaml's GC
from OCaml. But for extraction of C - you don't get any GC from Why3.

* F* / Low* / KaRaMeL

F* is one of the most interesting systems for this particular question.

Low* is explicitly designed to model C-like low-level computation. Its libraries model:

- stack allocation
- heap allocation
- C arrays
- machine integers
- C memory
- system-level C functionality

and KaRaMeL erases proofs before generating C.  GitHub

Conceptually:

#+begin_example
F* / Low*
    |
    | proofs
    | specifications
    v
verification
    |
    | erase proofs
    v
Low-level implementation
    |
    v
C
    |
    +--> stack
    |
    +--> heap
    |
    +--> explicit allocation
    |
    +--> no GC required
#+end_example

This is fundamentally different from:

#+begin_example
high-level functional language
             |
             v
             C
             |
             v
       generated GC runtime
#+end_example

Low* is specifically trying to model the C memory behavior rather than hide it behind a tracing collector.  GitHub

However, F* as a *whole* should not be labeled "no GC":

#+begin_example
F*
 |
 +--> OCaml backend       -> OCaml GC
 |
 +--> F# backend          -> .NET GC
 |
 +--> Low*/KaRaMeL -> C   -> can be GC-free
 |
 +--> other backends      -> depends
#+end_example

So F* gets a:

#+begin_example
"backend-dependent"
#+end_example

classification.

* Dafny

Dafny is almost the opposite example.

Suppose:

#+begin_example
Dafny
  |
  v
C++
#+end_example

It does *not* follow that you get "normal manual-memory C++".

Dafny has its own runtime/support infrastructure, and generated C++ can depend on that infrastructure.

Therefore:

#+begin_example
Dafny
 |
 v
C++
 |
 +--> Dafny runtime
 |      |
 |      +--> runtime representations
 |      +--> collections
 |      +--> memory management
 |
 v
program
#+end_example

The generated C++ can therefore effectively have managed-memory semantics even though C++ itself has no mandatory tracing GC.

This is exactly the phenomenon you were asking about.

So:

#+begin_example
C++ target
+
Dafny runtime
=
potentially GC/managed-memory behavior
#+end_example

* Verus

Verus is almost the opposite architectural model.

Verus verifies Rust and then removes ghost code before ordinary Rust compilation. Its documented pipeline says that specification/proof code is erased and the remaining code goes through normal rustc/LLVM compilation.  GitHub

#+begin_example
Rust
 |
 +-- executable code
 |
 +-- spec code
 |
 +-- proof code
 |
 v
Verus
 |
 | erase ghost
 v
Rust
 |
 v
rustc
 |
 v
native executable
#+end_example

Rust does not have a tracing GC as part of its normal execution model.

Therefore:

#+begin_example
Verus
  |
  +--> no Verus runtime
  |
  +--> no tracing GC
  |
  +--> ownership / borrowing
  |
  v
normal Rust binary
#+end_example

A programmer could of course implement a garbage collector *in Rust*. Verus does not prohibit that.

But that would be **application-level code**, not a hidden requirement of Verus.

* Isabelle/HOL

Isabelle's code generator produces SML, OCaml, Haskell and Scala.  Proofcraft+1

Therefore the memory-management story is inherited largely from the target:

#+begin_example
Isabelle/HOL
 |
 +--> SML      -> SML runtime / GC
 |
 +--> OCaml    -> OCaml GC
 |
 +--> Haskell  -> GHC GC
 |
 +--> Scala    -> JVM GC
#+end_example

So Isabelle doesn't need an "Isabelle GC".

But the generated program is certainly not necessarily GC-free.

* Agda

Agda is similar:

#+begin_example
Agda
 |
 +--> Haskell     -> GHC GC
 |
 +--> JavaScript  -> JS engine GC
#+end_example

Again:

#+begin_example
No Agda runtime
        !=
No garbage collector
#+end_example

* Lean

Lean is different.

Lean's executable model includes a runtime system, and its compiler targets native code through its compilation infrastructure.

Therefore I would not put Lean into the same category as:

#+begin_example
Why3 -> C
```

 or:

 #+begin\_example\
 Verus -\> Rust

```

where the output is naturally viewed as ordinary target-language code with the verifier's proof layer erased.

A more accurate model is:

#+begin_example
Lean
 |
 v
Lean compiler
 |
 v
native code
 |
 +--> Lean runtime
        |
        +--> runtime representations
        +--> memory management
        +--> GC/runtime machinery
#+end_example

* ACL2 / ATC

ACL2's ATC is interesting because it generates C and is explicitly designed as a proof-generating C code generator.

The conceptual model is:

#+begin_example
ACL2
 |
 | proof
 v
ATC
 |
 v
C
 |
 v
ordinary C compiler
#+end_example

ATC is much closer to:

#+begin_example
"generate C that follows the proved semantics"
#+end_example

than to:

#+begin_example
"generate C plus a large managed-language runtime"
#+end_example

So GC is **not normally intrinsic**.

Of course, nothing prevents the generated C program from linking against a GC library if the application requires one.

* Stainless

Stainless is more complicated.

Its Scala side naturally inherits Scala/JVM memory management:

#+begin_example
Stainless
 |
 v
Scala
 |
 v
JVM
 |
 v
GC
#+end_example

But GenC changes the picture:

#+begin_example
Stainless
 |
 v
GenC
 |
 v
C
 |
 +--> generated/support runtime
 |
 +--> allocator
 |
 +--> potentially explicit memory
#+end_example

Therefore I would classify Stainless/C as:

#+begin_example
backend-dependent
#+end_example

rather than simply "GC" or "no GC".

* SPARK

SPARK is Ada-based.

The normal SPARK model is much closer to:

#+begin_example
SPARK
 |
 v
Ada
 |
 +--> stack/static allocation
 +--> controlled heap allocation
 |
 v
native code
#+end_example

It does not require a tracing GC as part of the SPARK execution model.

This makes SPARK particularly relevant for safety-critical systems.

However, "Ada has no GC" should not be interpreted as a theorem about every possible Ada runtime. A particular Ada environment could theoretically provide additional managed facilities.

* Liquid Haskell

Liquid Haskell verifies Haskell rather than translating a separate language into C/Rust.

#+begin_example
Haskell + refinements
        |
        v
Liquid Haskell
        |
    refinements
      erased
        |
        v
      Haskell
        |
        v
       GHC
        |
        v
      GC/runtime
#+end_example

So:

#+begin_example
No Liquid Haskell runtime
        +
Haskell GC
#+end_example

is the right characterization.

* Vale

Vale operates at a much lower level.

Its generated/verified code can be incorporated into systems software without a mandatory tracing GC.

#+begin_example

"GC impossible"
#+end_example

You can implement a GC in assembly.

The relevant question is whether the *Vale-generated code requires one*. Normally, no.

* The really interesting distinction

There are actually **three independent axes**:

#+begin_example
                       GENERATED PROGRAM
                              |
             +----------------+----------------+
             |                                 |
          managed                         explicit
             |                             memory
             |                                 |
       +-----+-----+                    +------+------+
       |           |                    |             |
      GC         RC/other             malloc       ownership
       |                                /free        /regions
       |
       v
  runtime support
#+end_example

So "GC or no GC" is not the whole story.

For systems programming, I would use this richer classification:

| Memory model            | Examples                                                       | Main characteristic                                          |
|-------------------------+----------------------------------------------------------------+--------------------------------------------------------------|
| *Tracing GC*            | Dafny managed targets, Lean runtime, OCaml, Haskell, JVM/Scala | Automatic object reclamation                                 |
| *Reference counting*    | Possible in generated/runtime code                             | Deterministic reclamation but reference cycles need handling |
| *Ownership / borrowing* | Verus/Rust                                                     | Compile-time resource management                             |
| *Manual allocation*     | Low*/C, Why3/C, ordinary C                                     | Programmer/program proof controls allocation/deallocation    |
| *Regions / arenas*      | Low-level verified systems, some functional implementations    | Lifetime is controlled by region                             |
| *Stack/static*          | SPARK, Low* portions                                           | No general heap required                                     |
| *Hybrid*                | F*, Stainless, custom runtimes                                 | Different types/data structures can use different strategies |
| *Verified GC*           | CertiCoq/verified-GC research                                  | GC exists, but its behavior can itself be formally verified  |

* Bottom line

So, **yes: there absolutely are provers/formal-verification systems where the generated language is C/C++ but the resulting program can still have a garbage collector.**

The cleanest conceptual distinction is:

#+begin_example
                  C / C++
                     |
          +----------+----------+
          |                     |
       GC-based             GC-free
          |                     |
    runtime/collector       malloc/free
          |                 ownership
          |                 regions
          |                 arenas
          |                     |
    CertiCoq-style          Low*/KaRaMeL
    / Dafny-style           Why3/C
                            ACL2/ATC
#+end_example

And for the systems we've discussed, **Why3 deserves a particularly explicit “NO mandatory GC for C extraction” entry**. Its current documentation describes correct-by-construction OCaml extraction, while its recent release history documents C extraction; the C path should be considered separately from its OCaml path.  Why3+1

Likewise, **Low*/KaRaMeL is deliberately on the GC-free/manual-memory side**: its documentation explicitly models C stack/heap allocation and C memory, with proofs erased before C generation.  GitHub

And **Verus is on the ownership side**: after verification, ghost/specification code is erased and ordinary Rust compilation takes over.  GitHub

So if your ultimate target is something like **kernel/embedded/cryptographic code where you want *no GC, no VM, no special runtime, and ideally a conventional C/Rust binary***, the systems I'd investigate most closely are **F*/Low* + KaRaMeL, Why3/C, Verus/Rust, SPARK/Ada, ACL2/ATC, and Vale**. The functional extraction systems such as **Rocq/Coq, Isabelle and Agda** are excellent for a different point in the design space: they can eliminate the prover from deployment, but their normal functional-language targets themselves commonly use GC.
